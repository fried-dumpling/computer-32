# picalc — BBP 공식으로 π 10진수 자릿수 계산 (테스트용)

`program/picalc/pi.asm`. π를 **BBP(Bailey–Borwein–Plouffe) 공식**으로 16진수 4자리씩 계산하고, 그때마다 **×10으로 확정된 10진수 자리를 바로 뽑아서** 출력합니다. 정수 명령만 쓰고, 입출력은 `io` 라이브러리를 씁니다.

## 파일 (`program/picalc/`)

| 파일 | 역할 |
|---|---|
| `pi.asm` | 프로그램. 입력 처리, BBP limb 계산, 10진수 스트리밍(`dec_addlimb`, `dec_emit`, `dig_*`, `put_dig`), BBP 계산(`pi_frac`, `pi_series`, `pi_powmod`, `pi_fracdiv`) |
| `pi_test.py` | 빌드 후 에뮬레이터로 실행하고, Machin 공식으로 구한 정확한 자릿수와 비교합니다 |

## 빌드 / 실행

```
; program/ 에서
dasm picalc/pi.asm -o pi.o
dasm io/io.asm -o io.o
dlnk pi.o io.o -o picalc/pi.bin            ; 회로에 올릴 때는 -o ../boot/rom.bin
python ../tools/emu/isa32emu.py picalc/pi.bin "0 20\nq\n"
```

```
pi (BBP) - pos [count], q = quit
> 0 20
3.
0: 1415926535 8979323846
> 100 10
100: 8214808651
```

## 사용법

- 입력은 `시작위치 [개수]`입니다. 위치 0이 소수점 아래 첫 자리입니다.
  - 빈 줄은 `0 50`, `q`는 종료(`halt`). 개수를 생략하면 50(`DEFCOUNT`).
  - 개수가 0이면 아무것도 출력하지 않습니다.
  - 형식이 틀리거나 `위치 + 개수 > 1000`(`MAXDEC`)이면 `? pos [count]`를 출력합니다.
- 위치 0부터 시작하면 먼저 `3.`을 출력합니다.
- 자리가 확정되는 대로 바로 출력합니다(limb 하나에 4~5자리). 시작위치 앞의 자리도 계산은 하지만 출력하지 않습니다.
- 한 줄에 50자리(`PERLINE`), 10자리(`GROUP`)마다 공백, 줄 앞에 그 줄 첫 자리의 위치를 붙입니다.
- 메시지·프롬프트·입력 버퍼는 바이트 문자열이고, 글자는 `IO_LDB`로 읽습니다.

## 알고리즘

BBP는 **16진수 자리만** 독립적으로 뽑을 수 있습니다. 10진수 자리는 그렇게 할 수 없어서, 요청마다 위치 0부터 16진수를 계산하면서 10진수로 바꿔 나갑니다.

### 1. BBP (16진수)

π = Σ_k 16^-k (4/(8k+1) − 2/(8k+4) − 1/(8k+5) − 1/(8k+6))

frac(16^d π) = frac(4·S1 − 2·S4 − S5 − S6)

S_j = Σ_{k≤d} (16^(d−k) mod (8k+j)) / (8k+j) + Σ_{k>d} 16^(d−k) / (8k+j)

- **고정소수점**: 소수 부분을 `값 × 2^32`인 32비트로 표현합니다. 덧셈이 그대로 mod 1이 됩니다.
- **`pi_powmod`** (16^e mod m): e의 비트를 위에서부터 보면서 r = r² mod m, 비트가 1이면 r = 16r mod m(두 배 + 조건부 빼기 4번). 곱셈 명령이 없어서 r²은 shift-add이고, r < m이므로 m의 비트 수만큼만 돕니다. m = 1이면 0.
- **`pi_fracdiv`**: floor(r × 2^32 / m), r < m. 복원식 나눗셈으로 몫 32비트.
- **꼬리**(k > d): 16^-(k−d)/m = `fracdiv(1, m) >> 4(k−d)`, 7항.
- **값 범위**: 비교하는 값이 모두 2^31 미만이라 `cmp` + `neg`가 부호 없는 비교로 동작합니다(m < 2^30).
- **정밀도**: Python 모델로 위치 0~3090을 확인했을 때 오차가 최대 약 250 ulp(2^-32 단위).

### 2. limb (16진수 4자리)

- `x_d = pi_frac(d)`의 상위 16비트를 limb로 씁니다(d = 0, 4, 8, ...).
- x_d는 오차가 있어서 16비트 경계 근처에서 상위 16비트가 1 틀릴 수 있으므로 다음 chunk로 보정합니다.
  - `e = sext16(top16(x_(d+4)) − low16(x_d))`, `limb = (x_d + e) >> 16`
  - |오차| < 2^15이면 정확합니다(실제 오차는 2^8 정도).
  - x_d가 0 또는 2^32 경계(약 2^-24 확률)에 걸려 앞 limb로 올림이 넘어가야 하는 경우는 처리하지 않습니다.

### 3. 10진수 스트리밍 (limb가 올 때마다 ×10)

상태(모두 16비트 limb, word 하나에 하나):
- `sfrac` = frac(10^j · F_k): 지금까지 받은 limb k개의 소수 F_k에서 이미 출력한 j자리를 뗀 나머지(상위 limb가 앞).
- `pbig` = 10^j: 큰 정수(하위 limb가 앞).

limb L이 올 때마다:
1. **더하기** (`dec_addlimb`): `pbig × L`(16×16 shift-add)을 `sfrac`의 k번째 자리에 맞춰 더합니다. `sfrac` 맨 위에서 올림이 나가면 이미 출력한 자리에 +1(아래 보류).
2. **자리 뽑기** (`dec_emit`): `10 · pbig ≤ 2^16k`인 동안(`pbig` limb 수가 k보다 적거나, 같으면 최상위 limb가 6553(`PSAFE`) 미만) `sfrac`에 10을 곱해 정수 부분을 다음 자리로 내고, `pbig`에도 10을 곱합니다.
3. **보류** (`dig_in`, `dig_carry`, `dig_flush`): 출력한 자리로 넘어오는 올림은 최대 한 번이고 마지막 자리와 그 뒤의 9들까지만 닿습니다. 그래서 마지막 자리 h(`g_h`)와 뒤따르는 9의 개수(`g_n9`)를 들고 있다가, 9가 아닌 자리가 오면 출력하고, 올림이 오면 `h 9 … 9`를 `h+1 0 … 0`으로 바꿔 출력합니다. 끝에 남은 것은 `dig_flush`로 출력합니다.
- n자리에 약 n/4.8개의 limb가 듭니다. 버퍼는 `NLIMB = MAXDEC·27/128 + 16`(긴 9 연속 여유 포함)이고, 다 쓰면 들고 있던 자리를 그대로 출력하고 끝냅니다.
- Python 모델로 1000자리를 돌렸을 때 올림 43번, 그중 4번은 9를 들고 있을 때였습니다(358, 599, 667, 836번째 자리 근처). 결과는 모두 맞았습니다.

`cmp` 하나 뒤에 분기 두 개를 이어 쓰는 곳이 있습니다(`emit_lp`).

## 테스트

```
cd program/picalc
python pi_test.py --quick     # 위치 0..19, 100..104, 입력 오류
python pi_test.py             # 위치 0..99, 350..361, 빈 줄(0 50), 입력 오류
```

- 요청마다 출력을 나눠, 출력된 위치 집합과 각 자리를 정확한 값과 비교합니다. `3.` 줄도 확인합니다.
- 0..99에는 일반 올림이 5번, 350..361에는 9를 들고 있을 때의 올림(358 근처)이 있습니다.
- 입력 오류: `x`, `5 3 2`, `995 6`, `1001`. `0 0`은 출력이 없어야 합니다.
- **현재 결과 (2026-10-17)**: 에뮬레이터에서 ALL PASS. Digital 회로에서는 아직 돌리지 않았습니다. `quit:`의 `halt`가 calc와 똑같이 `jmp.one zero.32B, loop` 바로 뒤에 있어서, 같은 회로 문제로 시작하자마자 멈출 가능성이 큽니다(루트 `CLAUDE.md`). 회로에서 돌릴 때는 `halt`를 `jmp.one pc.32B, 0`으로 바꾸세요.

### 성능 (에뮬레이터 명령 수)

| 요청 | 명령 수 |
|---|---|
| `0 10` | 약 8.5만 |
| `0 20` | 약 19만 |
| `0 50` | 약 84만 |
| `0 100` | 약 320만 |
| `350 12` | 약 5,300만 |

- 시간은 거의 BBP가 차지합니다. chunk 하나의 비용이 대략 d·log²d에 비례해서, 전체는 자리 수의 제곱보다 조금 빠르게 늘어납니다.
- Digital 시뮬레이션에서는 수십 자리 정도가 현실적입니다.
